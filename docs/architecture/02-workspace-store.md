# Workspace store

## Summary

**Kind:** subsystem

The effectful shell around the pure core: it owns every workspace JSON file on disk, the locks
that serialize writes to one, and the transaction boundary each mutation commits inside.

## Purpose

This is where pasta stops being a set of pure functions and starts being a server with state. It
exists to keep *all* effects in one place — file reads and writes, lock acquisition, id and
revision-token generation, clock reads — so that `commands`, `render`, `describe`, and the
page-type layer can be pure and unit-testable with no filesystem.

It also owns the two guarantees a concurrent authoring client depends on: a batch of commands
commits atomically or not at all, and a stale writer is told it is stale instead of silently
overwriting a newer revision. Delete this component and those guarantees have nowhere to live —
each caller would have to re-implement read-modify-write against the same file.

**The pure/effectful line runs at this component's own boundary**, and it runs *inside*
`mutate_page_batch`: the loop decides nothing itself, it calls `commands.apply_command` for every
decision and performs the one write that results. `Store` is the only component in `src/` that
touches the filesystem for workspace data.

## Usage

`Store` is constructed once per process with a root directory — `Store(DATA_DIR)` in
`src/server.py` — and every method takes a `workspace_id` as its first argument. There is no
open/close lifecycle; each call loads, acts, and (for writes) saves.

The 56 methods group into:

- **Reads:** `load_workspace`, `list_workspaces`, `get_page`, `tree`, `outline`,
  `render_markdown`, `render_html`, `search`
- **Direction:** `next_actions`, `attention` — the self-directing surface
- **Page writes:** `create_page`, `mutate_page_batch`, `set_page_status`, `archive_page`,
  `unarchive_page`, `reparent_page`, `reorder_page`, `rename_page`, `link_page`, `unlink_page`
- **Workspace writes:** `create_workspace`, `archive_workspace`, `unarchive_workspace`,
  `set_workspace_guidance`
- **Maintenance:** `cleanup_workspace`, `write_backup`

Required order for a write: every command in a `mutate_page_batch` call must carry the page's
current `statusRevisionToken`, which a caller obtains from a prior read (`getPage`,
`nextActions`, or the `next` block echoed by the previous write). A status transition regenerates
that token, so a batch holds **at most one transition, and only as its final command**.

For dependency injection, the constructor takes `id_factory` and `revision_factory`; tests pass
deterministic counters instead of `ids.default_id_factory` / `default_revision_factory`.

## Data model

**On disk:** one JSON file per workspace under the store root, named
`<workspace_id with ':' → '_'>.json` — `:` is not a legal Windows filename character, so the
true id lives inside the file and `_id_for_path` inverts the mapping for listing. Backups go to
`backups/<token>/<YYYYMMDDTHHMMSSZ>.json`, colon-free for the same reason.

The file content is `serialize.workspace_to_dict` output: a near-identity mapping of the
`Workspace` dataclass, written with `indent=2` and `ensure_ascii=False`. Field values are already
JSON-able, so the on-disk shape is stable independently of the dataclass internals.

**Persisted:** everything in `Workspace` and `Page` — ids, titles, statuses, `child_ids`,
`sections`, `links`, `archived`, `guidance_config`, `created_at`/`updated_at`, plus the two
store-owned fields below. **Derived, never stored:** markdown and HTML renderings, `tree` and
`outline` projections, search snippets, and the whole `next_actions` partition — all recomputed
per call from the page type plus the page.

Two `Page` fields are owned by this component and **never** written by a page-type command:

- `status_revision_token` — a short optimistic-concurrency stamp, created with the page and
  regenerated by `_next_revision` on every status transition. `_next_revision` loops until the
  new token differs from the current one, so a token a caller still holds can never accidentally
  re-match the page after it moved.
- `expires_at` — written and cleared only by the cleanup sweep (component 10).

**In memory, per process:** two lock tables keyed by workspace id, guarded by `_locks_guard`:
`_transaction_locks` (a `threading.Lock` per workspace, taken only by writers) and `_rw_locks`
(a `ReadWriteLock` per workspace, taken per file operation by both readers and writers).

## Details

The transaction shape is the same in every write method: take the transaction lock, load, act,
`_touch_and_save`. `mutate_page_batch` is the elaborate case, because it must decide a whole
ordered batch against a working copy:

```python
with self._transaction_lock_for(workspace_id):
    workspace = self.load_workspace(workspace_id)
    ...
    working = page
    stored_revision = page.status_revision_token   # the revision on disk
    for index, entry in enumerate(batch):
        ...
        if presented_revision != working.status_revision_token:
            raise ConflictError(self._revision_conflict(...))
        result = commands.apply_command(working, page_type, command, args, ...)
        working = result.page
        if working.status != status_before:
            working.status_revision_token = self._next_revision(...)
    workspace.pages[page_id] = working
    self._touch_and_save(workspace)
```

Each command is decided against the state the previous one left, and nothing is written until the
loop completes — so a rejection at index *n* discards the work of `0..n-1` entirely. The error
message names the failing index and command.

`_revision_conflict` handles a subtlety that is easy to get wrong: a transition earlier in the
same batch regenerates the token *in memory*, but an abort writes nothing, so that regenerated
token dies with the batch. The message therefore reports `stored` — the revision the page
actually keeps — rather than the one the discarded working copy had reached, and says which to
present on retry.

Two lock tiers, with different jobs:

- `_transaction_lock_for` — serializes write transactions so no update is lost. **Readers never
  take it**, so a long batch never blocks a browser read.
- `_rw_lock_for` — a writer-preferred `ReadWriteLock` held for the duration of a single file
  operation, keeping a reader out of the `os.replace` that swaps a workspace file. One lock per
  workspace covers every file it is stored in, backups included.

Writes are atomic at the filesystem level: `_write_file` serializes to a temp file named with the
pid and thread id, then `os.replace`s it into position under the write lock, with a single
sleep-and-retry because a Windows permission error moving the temp file is transient.

`next_actions` is the component's most intricate read, and it is pure computation over a loaded
workspace. It partitions model-declared edges into `do` (agent edges to drive now), `blocked`
(with the unmet precondition named), `humanGates` (sign-off — stop), and `attention`. One
precedence rule is load-bearing: a **parent-state guard outranks unmet content**. While a parent
has not unlocked a stage, the child's field setters are withheld from `do` and the block reason
names the parent — because naming the fields would point an agent at work that is not due yet.

The graph shows this component and the transport co-clustered six times (`Cluster_1`,
`Cluster_74`, `Cluster_75`, `Cluster_77`, `Cluster_79`, `Cluster_81`), each cluster pairing a tool
with its store method. `load_workspace` has 21 callers and `_transaction_lock_for` 13 — the
highest fan-in inside the subsystem, and the reason a change to either is worth an `impact` run
first. `Cluster_96` is store-internal only; `ids.py` holds `Cluster_40` and `Cluster_41`.

## Invariants

1. **A rejected batch writes nothing.** The loop mutates a working copy and calls
   `_touch_and_save` only after every command has succeeded. Violated, a partially applied batch
   leaves a page in a state no command sequence could have produced — for example past a
   transition whose required content was never accepted.
2. **Every command in a batch presents the page's current `status_revision_token`.** Checked per
   command before `apply_command`. Violated, a client working from a stale read silently
   overwrites a newer revision, and the lost update is undetectable after the fact.
3. **A batch contains at most one status transition, and only as its final command.** Enforced
   structurally: a transition regenerates the token, so any later command in the same batch
   carries a stale one and aborts. Violated, a page could cross two FSM edges in one commit with
   only the first one's preconditions ever checked.
4. **`_next_revision` never returns the token it replaces.** It loops until the value differs.
   Violated, a stale token can re-match a page that has since moved, defeating the conflict check
   exactly when it matters.
5. **No workspace file is ever observed half-written.** Writes go to a pid+thread-unique temp file
   and land via `os.replace` under the write lock. Violated, a concurrent reader parses a
   truncated file and the workspace reports as corrupt.
6. **Only the store writes `status_revision_token` and only the sweep writes `expires_at`.**
   Violated, a page-type command could forge a revision stamp or an expiry, making the
   concurrency check and the deletion deadline both unreliable.
7. **A write transaction never blocks a read.** Readers take only the per-file `ReadWriteLock`,
   never `_transaction_locks`. Violated, a long batch stalls every browser request for that
   workspace.
